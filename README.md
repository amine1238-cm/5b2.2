# Resource Platform MVP – Increment 3

This local-development scaffold contains users, roles, departments, locations, resource types, resources, administrator resource editing, signed sessions, migrations, fictional seed data, and basic audit logging.

## Requirements

- Python 3.11 or newer
- The runtime dependencies `reportlab>=4.0,<5.0` and `cryptography>=42.0,<51.0` are required for real QR-code SVG generation. Install project dependencies with `python -m pip install -e ".[test]"`.

## Setup and commands

Run all commands from the project root. The project includes setuptools package configuration, so `resource_platform` is importable from the project root and after editable installation.

### Show migration help

```bash
python -m resource_platform.database --help
```

### Apply migrations

Use an explicit database path for a new database:

```bash
python -m resource_platform.database migrate --database-path ./resource_platform.sqlite3
```

If `--database-path` is omitted, the command uses `DATABASE_PATH`; otherwise it uses the development path defined by the application configuration:

```bash
python -m resource_platform.database migrate
```

Migrations create the database if necessary, record applied versions in `schema_migrations`, and are safe to run repeatedly. Migrations never insert seed data.

### Insert fictional development seed data

```bash
python -m resource_platform.seed
```

Seeding is always explicit. It inserts only fictional users and resources and must not be run against production data.

### Start the application

```bash
python -m resource_platform
```

The default local URL is `http://127.0.0.1:8000/login`.

WSGI import path:

```python
from resource_platform.wsgi import application
```

### Run tests

```bash
python -m unittest discover -s tests -v
```

Tests create isolated temporary databases and never use the development database.

### Run compilation checks

```bash
python -m compileall -q resource_platform tests
```

Vehicle fuel tracking, maintenance, notifications, Outlook, reports, and file uploads are not implemented.

## Booking increment

Apply migrations, including bookings:

```bash
python -m resource_platform.database migrate --database-path ./resource_platform.sqlite3
```

Bookings store UTC ISO-8601 timestamps with offsets. User input is interpreted in `Europe/Berlin`; ambiguous or nonexistent daylight-saving transition times are rejected rather than silently shifted. Confirmed-booking overlap is prevented by a SQLite trigger and an application transaction using `BEGIN IMMEDIATE`. Cancelled bookings do not block availability.

Resources can be viewed at `/resources`, booked from their availability page, and reviewed at `/bookings`.

## QR codes and lifecycle

Install dependencies:

```bash
python -m pip install -e ".[test]"
```

Migration 0004 creates QR tokens, checkouts, and checkins; migration 0005 permits a documented administrator checkout override without a booking. Migration 0006 adds override metadata and migration 0007 adds encrypted active-token storage. There is no unused key-version migration. QR tokens contain at least 256 bits of randomness, only SHA-256 hashes are stored, and regeneration invalidates the prior token. QR output is SVG generated by ReportLab and contains only the opaque resource URL. PNG QR decoding is tested with OpenCV. Install the test dependencies with:

```bash
python -m venv .venv
.venv/bin/python -m pip install -e ".[test]"
.venv/bin/python -m unittest discover -s tests -v
```

On Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[test]"
.venv\Scripts\python.exe -m unittest discover -s tests -v
```

The decoder integration test is explicitly enabled with `RUN_QR_DECODER_TESTS=1`; without that variable it is reported as skipped with an explicit reason. SVG and PNG are generated from the same opaque resource URL function. SVG scannability is not claimed unless decoded by a real decoder.

Authenticated users may perform lifecycle actions only after server-side permission and state checks. Unauthenticated QR pages expose minimal resource information only.

### QR encryption key management

The active QR token is encrypted with Fernet before it is stored so the same QR can be printed repeatedly without rotating it. The encryption key is never stored in the database or source code. Configure a separate key per environment using `QR_TOKEN_ENCRYPTION_KEY`; generate one with:

```bash
.venv/bin/python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Store the value in the environment or an external secret manager, not `.env` committed to source control. Key rotation requires controlled migration: retain the old key for decryption, re-encrypt active tokens with the new key, then remove the old key. If an active token cannot be decrypted, printing fails closed and does not silently rotate or invalidate the printed QR; an administrator must regenerate it after key recovery.

The QR print response contains the rendered QR image and safe resource label information, but does not expose the raw token as visible text, in a `data-*` attribute, JSON, or an ordinary hyperlink. Printing reuses an active token; only the explicit regeneration action invalidates it. Key rotation is a production-hardening task and is not implemented in this MVP.


## Increment 5A database backend abstraction

SQLite remains the only implemented runtime backend in Increment 5A. Local development and tests use an isolated `DATABASE_PATH`:

```bash
DATABASE_BACKEND=sqlite
DATABASE_PATH=./resource_platform.sqlite3
```

`DATABASE_URL` is parsed and validated for the future PostgreSQL backend, but selecting `DATABASE_BACKEND=postgresql` currently fails clearly before any connection is attempted. PostgreSQL runtime operations and PostgreSQL migrations are intentionally deferred to Increment 5B.

Run the test suite with:

```bash
python -m unittest discover -s tests -v
python -m compileall -q resource_platform tests scripts
```


## Increment 5B1 PostgreSQL schema migrations

Increment 5B1 adds PostgreSQL-compatible schema migrations only. PostgreSQL application CRUD, connection pooling, bookings, QR operations, checkout, and check-in runtime support are not implemented yet. SQLite remains the only application runtime backend.

Requirements:

- PostgreSQL 16 for schema verification.
- `btree_gist` extension, enabled by the PostgreSQL migration.
- A test-only `DATABASE_URL`, for example:

```text
postgresql://resource_test:password@127.0.0.1:5432/resource_platform_test
```

Apply PostgreSQL schema migrations:

```bash
python -m pip install -e ".[test]"
python -m resource_platform.postgresql_migrations migrate --database-url "$DATABASE_URL"
python -m resource_platform.postgresql_migrations migrate --database-url "$DATABASE_URL"
```

The first run applies seven logical migrations; the second applies zero. The PostgreSQL manifest is `migrations_postgresql.manifest.json`. Existing SQLite migrations and its manifest are unchanged. PostgreSQL tests are intentionally run explicitly because they require a live PostgreSQL service and must fail, not skip, when that service is unavailable.


## Increment 5B2.1 PostgreSQL runtime connectivity

Increment 5B2.1 adds PostgreSQL connection and pooling primitives only. PostgreSQL application CRUD, login, booking, QR, checkout, and check-in runtime operations remain deferred.

Install the PostgreSQL runtime dependency with:

```bash
python -m pip install -e ".[test]"
```

Configure:

```text
DATABASE_BACKEND=postgresql
DATABASE_URL=postgresql://user:password@host:5432/database
DB_POOL_MIN_SIZE=1
DB_POOL_MAX_SIZE=10
DB_CONNECTION_TIMEOUT_SECONDS=5
DB_POOL_ACQUISITION_TIMEOUT_SECONDS=5
DB_HEALTH_CHECK_TIMEOUT_SECONDS=3
DATABASE_SSLMODE=prefer
```

The PostgreSQL backend uses `psycopg[binary,pool]`, dictionary-compatible rows, explicit transactions, bounded pool acquisition, health checks, broken-connection disposal, and clean pool shutdown. SQLite continues to use direct connections and the existing SQLite behavior. No PostgreSQL connection is made during module import.


## Increment 5B2.1 runtime primitives

Increment 5B2.1 adds psycopg-based PostgreSQL connection and pooling primitives only. PostgreSQL application CRUD and business routes remain deferred. SQLite continues to use direct connections. Install with `python -m pip install -e ".[test]"`; PostgreSQL tests require a live PostgreSQL service and must be run in the dedicated CI job.
